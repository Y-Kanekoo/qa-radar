      第1章 Webアプリケーションとは

      Webアプリケーションとは、ブラウザ(クライアント)とサーバーという2台の コンピューター(プログラム)が、HTTPという共通言語で会話しながら動く仕組みです。 あなたのスマホでSNSを見るのも、ネットショッピングも、全部この形です。

      大事な原則: 会話は必ずクライアントから始まること、そして 1回のリクエストには必ず1回のレスポンスが返ることです。 実験室のX-Rayパネルで見た「往復」がまさにこれです。

      第2章 URLのしくみ

      URLは「どのサーバーの、どの資源が欲しいか」を表す住所です。分解してみましょう。

      • localhost は「このコンピューター自身」を指す特別な名前。本アプリはあなたのPCの中でサーバーが動いています。
      • 普段見る https://example.com/... では、DNSという仕組みがホスト名を IPアドレス(コンピューターの番号)に変換してくれます。
      • ポート 8000 は「そのコンピューターの8000番窓口」。1台のPCで複数のサーバーが動けるのは窓口番号があるからです。

      第3章 HTTP — リクエストとレスポンス

      HTTPの正体は、決まった書式のただのテキストです。X-Rayパネルの 「📤リクエスト」「📥レスポンス」タブに出ていたものが、ほぼそのまま実物です。

      リクエストの構造

      POST /api/todos HTTP/1.1   ← ①リクエスト行 (何をどこに)
Host: localhost:8000        ← ②ヘッダー (メモ書き)
Content-Type: application/json
                            ← ③空行 (ここまでがヘッダーの合図)
{"title": "牛乳を買う"}      ← ④ボディ (送るデータ本体)

      レスポンスの構造

      HTTP/1.1 201 Created        ← ①ステータス行 (結果)
Content-Type: application/json
Content-Length: 312         ← ②ヘッダー
                            ← ③空行
{"ok": true, "data": {...}} ← ④ボディ (返すデータ本体)

      ボディに使われている {"title": "牛乳を買う"} という書き方が JSON(JavaScript Object Notation)。プログラム同士がデータを渡し合うときの、 現在もっとも標準的な形式です。

      第4章 HTTPメソッドとステータスコード

      メソッドは「リクエストの動詞」。このアプリでは操作とメソッドが1対1に対応しています。

      メソッド意味このアプリでの例
      GETちょうだい (取得)TODO一覧の読み込み
      POST新しく作って (作成)TODOの追加
      PATCH一部を変えて (部分更新)完了チェックの切り替え
      DELETE消して (削除)TODOの削除

      ステータスコードは「レスポンスの結果を表す3桁の数字」。先頭の数字でグループ分けされています。

      コード意味このアプリで体験する場面
      200 OK成功一覧取得・更新・削除の成功
      201 Created作成に成功TODO追加の成功
      400 Bad Requestあなたの送信内容が変 (4xx=クライアント側の問題)💥実験: 空タイトルを送る
      404 Not Foundそんなものは無い💥実験: 存在しないIDを削除
      500 Internal Server Errorサーバー側の事故 (5xx=サーバー側の問題)server.py にバグを仕込むと見られる

      第5章 フロントエンドの3点セット (HTML / CSS / JS)

      ブラウザ側で動くものをフロントエンドと呼びます。役割の違う3種類のファイルで作ります。

      ファイル役割たとえるなら
      index.html構造 — 何がどこにあるか家の骨組み
      style.css見た目 — 色・配置・大きさ内装・塗装
      app.js動き — クリックに反応し、サーバーと通信電気配線と家電

      特に重要なのが JavaScript の fetch() です。 昔のWebは「何かするたびページ全体を再読込」していましたが、fetch を使うと ページを開いたまま裏でHTTP通信し、画面の必要な部分だけ描き換えられます。 TODOを追加したとき画面がチカッと白くならないのはこのためです。

      もうひとつの鍵は DOM。ブラウザはHTMLを「部品の木構造」としてメモリに持っていて、 JavaScriptから document.createElement("li") のように部品を追加・削除できます。 このアプリのTODO一覧は、サーバーから来たJSONをもとに app.js が組み立てています。

      第6章 バックエンド(サーバー)の仕事

      サーバー側のプログラムをバックエンドと呼びます。本アプリでは server.py の約400行がすべてです。仕事は主に4つ:

      1. ルーティング — 「URLとメソッド」を見て、担当する関数を決める対応表引き。 POST /api/todos → create_todo() のように。
      2. バリデーション — 受け取ったデータが正しいか検査する。フロント側でも検査するが、 サーバー側の検査は省略できない (ブラウザを介さず curl などで直接リクエストを送れてしまうから)。
      3. ビジネスロジック — アプリ固有の処理。DBへの読み書きの指揮。
      4. レスポンス生成 — 結果をJSONにまとめ、適切なステータスコードで返す。

      X-Rayパネルの「⚙️サーバー内部」タブは、この4つの仕事がリクエストのたびに 順番に実行されている記録そのものです。FlaskやFastAPIといった 「Webフレームワーク」は、この定型作業を楽にしてくれる道具にすぎません。

      第7章 データベースとSQL

      サーバーのプログラムは再起動すると変数の中身を忘れます。そこでデータは データベース(DB)に永続保存します。本アプリはSQLiteという 「1個のファイルがそのままDBになる」軽量DBを使っています (data/todos.db)。

      DBの中は表(テーブル)の形をしています。TODOはこう保存されています:

      idtitledonecreated_at
      1牛乳を買う02026-07-27 03:00:00
      2本を返す12026-07-27 03:05:00

      DBとの会話に使う言語がSQL。基本の4文がTODOの4操作にそのまま対応します。

      SELECT id, title, done, created_at FROM todos ORDER BY id;  -- 読む   (GET)
INSERT INTO todos (title) VALUES (?);                       -- 作る   (POST)
UPDATE todos SET done = ? WHERE id = ?;                     -- 変える (PATCH)
DELETE FROM todos WHERE id = ?;                             -- 消す   (DELETE)

      ⚠️ ? はプレースホルダー。ユーザー入力をSQL文字列に直接つなぐと、 入力に紛れ込ませたSQLが実行されてしまう「SQLインジェクション」という 攻撃を受けます。必ず ? 経由で値を渡す — これはWeb開発の鉄則です。

      第8章 1回の操作を通しで追う

      「牛乳を買う」を追加したときに起きること全部を、時系列で並べます。

      1. 🖥 ブラウザ: [追加]ボタンで form の submit イベントが発生。app.js が入力値を取り出し、fetch("/api/todos", {method:"POST", ...}) を実行
      2. 📮 通信: HTTPリクエスト(テキスト)がTCPという通信路に乗ってサーバーへ届く
      3. 🖧 サーバー: ルーティング表から create_todo() を選ぶ → JSONボディを解析 → タイトルが1〜100文字か検査
      4. 🗄 DB: INSERT INTO todos (title) VALUES (?) で1行追加。新しい id が採番される
      5. 🖧 サーバー: 追加した行を読み直し、debug記録と一緒にJSON化。201 Created で送信
      6. 📬 通信: HTTPレスポンスがブラウザへ戻る
      7. 🖥 ブラウザ: app.js がJSONを受け取り、<li> 要素を作って一覧に追加。ページ遷移なしで画面が更新される

      実験室の「旅の地図」はこの流れの再現です。じっくりモードをONにして、 もう一度追加操作をしながら1ステージずつ確かめてみてください。

      第9章 開発者ツールで本物を覗く

      X-Rayパネルは学習用に整形した表示ですが、ブラウザには本物の観察装置 「開発者ツール」が最初から入っています。F12キー (Macは Cmd+Option+I) で開けます。

      • Network タブ — このページの全HTTP通信が見える。TODOを追加して、todos という行をクリックし、Headers / Payload / Response を見比べよう。X-Rayパネルと同じ内容のはず
      • Elements タブ — いまブラウザが持っているDOM(HTMLの木)。TODOを追加すると <li> がその場で増える様子が見える
      • Console タブ — JavaScriptの実行環境。fetch("/api/todos").then(r => r.json()).then(console.log) と打てば、自分の手でAPIを呼べる

      「X-Rayパネルで仕組みを掴む → 開発者ツールで本物を確認する」の往復が、 このアプリの卒業条件です。

      第10章 このアプリ自身の構成

      いま使っているこのアプリも、学んだ通りの部品でできています。

      learning-lab/
├── server.py          ← バックエンド (Python・約400行・全行コメント付き)
├── static/
│   ├── index.html     ← 骨組み (この教科書の本文もここ)
│   ├── style.css      ← 見た目
│   └── app.js         ← 動き (fetch通信・X-Ray描画)
└── data/todos.db      ← データベース (SQLiteファイル・初回起動時に自動生成)

      仕上げの学習として、ぜひコードを読んで・壊して・直してください。おすすめ:

      • server.py の TITLE_MAX_LEN を 10 に変えて再起動 → 11文字で400になることを確認
      • app.js の一覧描画を書き換えて、完了済みTODOに取り消し線以外の装飾を足す
      • 新しいAPI GET /api/todos/count を自分で追加してみる (ルーティング表に1行+関数1つ)

      設計の全体像は DESIGN.md、発展課題は README.md にあります。
